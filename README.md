# 한양여자대학교 규정집 파서 & 규정 정합성 평가 대시보드

이 저장소는 두 개의 도구로 구성됩니다.

| 도구 | 역할 |
|---|---|
| [regulation_parser.py](regulation_parser.py) | 그룹웨어 규정집을 수집·파싱하여 SQLite DB와 클러스터별 텍스트 파일을 생성 |
| [streamlit_dashboard.py](streamlit_dashboard.py) | 파서가 만든 규정 텍스트를 FactChat Agent 로 보내 정합성을 분석하고 결과를 대시보드로 표시 |

데이터 흐름:

```
그룹웨어 규정집 ──▶ regulation_parser.py ──▶ regulations.db
                                          └▶ regulationsByCluster/*.txt ──▶ streamlit_dashboard.py
                                                                             └▶ FactChat Agent 분석 ──▶ 대시보드 표시
                                                                                                       └▶ analysis_store.json (결과 영구 저장)
```

---

# 1. regulation_parser.py — 규정집 파서

한양여자대학교 그룹웨어 규정집(https://gw.hywoman.ac.kr/ekp/ruleweb/index.do)의
규정 트리를 순회하며 규정 메타데이터와 PDF 본문 텍스트를 수집하여
SQLite DB에 저장하고, 전체 규정을 하나의 텍스트 파일로 통합하는 도구입니다.

## 주요 기능

### 1. 규정 트리 수집
- 그룹웨어 규정집의 분류 트리를 재귀적으로 순회하여 전체 규정 목록을 수집합니다.
- 각 규정의 상세 정보(규정번호, 제·개정일자, 관리부서 등)를 API로 조회합니다.
- 서버 부하 방지를 위해 요청 간 지연(`REQUEST_DELAY`, 기본 0.2초)을 둡니다.

### 2. PDF 본문 텍스트 추출
- 규정 PDF 파일을 내려받아 `pymupdf`로 텍스트를 추출합니다.
- 내려받은 PDF는 `pdf_cache/` 폴더에 캐시됩니다(디버깅/재검증용).
- **좌표 기반 재구성 폴백**: 텍스트 레이어 순서가 깨진 PDF(일부 HWP 변환본)는
  글자별 좌표(bbox)를 이용해 시각적 순서(위→아래, 왼쪽→오른쪽)로 재구성합니다.
  이때 공백이 `&`, `!`, `$` 등의 글리프로 잘못 매핑된 경우
  빈도 분석(전체의 0.5% 이상)으로 감지하여 공백으로 치환합니다.
- **제어문자 제거**: PDF 텍스트 레이어에 섞여 나오는 U+0001 등의 제어문자
  (개행/탭 제외)를 모두 삭제합니다.
- **표 구조 보존**: 페이지의 표(2행 2열 이상)를 감지하여 평문 대신
  `[표] 셀1 | 셀2 ; 셀1 | 셀2 [표끝]` 형태(셀 구분 `|`, 행 구분 `;`)의
  직렬화 텍스트로 해당 위치에 삽입합니다.

### 3. 본문 구조화 파싱
- 본문 시작점(제1장 또는 제1조)부터 파싱을 시작합니다.
- 장(章)/절(節)/조(條)/부칙 단위로 세그먼트를 분할하고,
  페이지 번호 등 노이즈 줄을 제거합니다.
- 문서 끝의 `[별표 N]`, `[별지 제N호 서식]`은 장과 동일한 독립 세그먼트로
  분리하여 마지막 별표까지 빠짐없이 포함합니다.
- 모든 장/조 앞에 `(규정명)` 접두어를 삽입하고,
  장 사이는 빈 줄(`\n\n`), 조 사이는 줄바꿈(`\n`)으로 구분합니다.

### 4. SQLite DB 저장 (`regulations.db`)
- 규정명을 기본키로 하여 `regulations` 테이블에 upsert합니다.
- 재실행 시 동작:
  - **신규추가**: DB에 없는 규정은 새로 저장
  - **업데이트**: 개정일자가 DB구성날짜보다 나중인 규정만 다시 처리
  - **재시도**: 본문 추출이 비어 있는 레코드는 다시 처리
  - **변경 없음**: 그 외에는 건너뜀
- 폐지규정(`deleteYn = "Y"`)은 처리하지 않고 건너뜁니다.

### 5. 사라진 규정 정리 (`regulations_delete.db`)
- 사이트 트리에서 사라진 규정은 `regulations.db`에서 삭제하고
  `regulations_delete.db`로 이동시킵니다(이동 시점을 `삭제날짜` 컬럼에 기록).
- 상세정보 조회 실패가 1건이라도 있으면 오삭제 방지를 위해
  해당 실행에서는 정리를 건너뜁니다(다음 정상 실행 때 자동 정리).

### 6. 통합 텍스트 내보내기
- 본문이 있는 전체 규정을 규정번호 순으로 정렬하여
  `한양여자대학교_{N}개의 규정통합(연도.월.일).txt` 파일로 저장합니다.
- 규정 사이는 빈 줄 2개(`\n\n\n`)로 구분됩니다.

### 7. 클러스터별 규정 저장 (`regulationsByCluster/`)
- `주제별 클러스터.txt`(A~K 클러스터 정의, 수동 관리)를 읽어
  DB의 규정을 주제별로 분류하고 `regulationsByCluster/<클러스터명>.txt`로 저장합니다.
- 규정명 표기 차이(공백·가운뎃점·괄호 설명 등)를 흡수하기 위해
  정규화 후 부분일치 + 부분수열 방식으로 매칭합니다.
- 파일이 **150KB(utf-8 기준)를 넘으면 규정 경계에서 분할**하여
  `A1. ….txt`, `A2. ….txt`처럼 넘버링해 저장합니다.
  (FactChat Agent 1회 호출당 입력 크기 제한에 맞추기 위한 분할이며,
  대시보드는 분할 파일 수만큼 API를 반복 호출합니다.)
- 어느 클러스터에도 속하지 않은 규정은 로그로 경고합니다.

### 8. 실행 로그 저장 (`run_log/`)
- 콘솔에 출력되는 모든 로그를 `run_log/run_log_연도.월.일.txt`에도 기록합니다.
- 같은 날 여러 번 실행하면 이어서 기록되며(append),
  실행마다 `===== 실행 시작: ... =====` 타임스탬프 구분선이 들어갑니다.

## 실행

```powershell
python regulation_parser.py
```

실행하면 다음 순서로 진행됩니다.

1. 규정 트리 순회 → 전체 규정 목록 수집
2. 규정별 신규/업데이트/재시도 판단 후 PDF 다운로드 및 텍스트 추출
3. 트리에서 사라진 규정을 `regulations_delete.db`로 이동
4. 통합 텍스트 파일 / 클러스터별 텍스트 / 규정목록.txt 생성
5. 처리 결과 요약 출력 (`신규 N, 업데이트 N, 건너뜀 N, 실패 N`)

첫 실행은 전체 규정을 내려받아 수 분이 걸리며,
이후 재실행은 변경된 규정만 처리하므로 빠르게 끝납니다.

## DB 스키마 (`regulations` 테이블)

| 컬럼 | 설명 |
|---|---|
| 규정명 | 규정 이름 (기본키) |
| 분류명 | 규정집 상위 분류 (예: 학칙, 행정 등) |
| DB구성날짜 | 해당 레코드를 저장/갱신한 날짜 |
| 규정번호 | 예: `4-3-1` |
| 규정버전 | 그룹웨어상 버전 번호 |
| 규정파일링크 | 원본 PDF 다운로드 URL |
| 제정일자 / 개정일자 | 규정 제·개정 일자 |
| 조회수 | 그룹웨어 조회수 |
| 관리부서 / 관련부서 | 담당 부서 |
| 텍스트추출내용 | 구조화 파싱된 본문 텍스트 |

`regulations_delete.db`는 동일 스키마에 `삭제날짜` 컬럼이 추가되어 있습니다.

# 2. streamlit_dashboard.py — 규정 정합성 평가 대시보드

파서가 생성한 클러스터별 규정 텍스트(또는 업로드한 제·개정규정 PDF)를
**FactChat Agent**(OpenAI 호환 API)로 전송하여 상위법령·대학규정 간
정합성을 분석하고, 결과(불일치/검토 필요 이슈)를 대시보드로 표시합니다.

## 실행

```powershell
python streamlit_dashboard.py
# 또는
streamlit run streamlit_dashboard.py
```

`python`으로 직접 실행하면 Streamlit 실행 컨텍스트가 아님을 감지하고
자동으로 `streamlit run`으로 재시작합니다.

## API 키 설정

FactChat API 키는 다음 두 곳 중 하나에 설정합니다(둘 다 있으면 secrets 우선).

1. `.streamlit/secrets.toml` — **TOML 형식이므로 값을 반드시 따옴표로 감싸야 합니다.**
   ```toml
   FACTCHAT_API_KEY = "발급받은 키"
   ```
2. `.env` — 환경변수 폴백
   ```
   FACTCHAT_API_KEY=발급받은 키
   ```

두 파일 모두 `.gitignore`에 등록되어 있어 커밋되지 않습니다.
OpenAI SDK 클라이언트는 `@st.cache_resource`로 캐시되어 세션 간 재사용됩니다.

## 탭 1 — 현행규정 정합성

현행 대학규정과 상위법령 간 정합성을 클러스터 단위로 분석합니다.

1. **클러스터 선택**: 주제별 클러스터 A~K 중 하나를 선택합니다.
2. **정합성 분석 실행**: `regulationsByCluster/` 폴더에서 선택한 클러스터 ID로
   시작하는 txt 파일을 모두 찾습니다(150KB 초과로 분할된 `A1`, `A2`…도 번호순 포함).
   파일 1개당 `분석모드:현행규정 / 선택클러스터:{ID} / [첨부파일]` 프롬프트로
   **FactChat API를 1회씩 호출**하고, 분할 호출 결과를 하나로 합산합니다.
3. **결과 저장·표시**: 합산된 JSON을 대시보드 데이터로 변환해 표시하고
   `analysis_store.json`에 클러스터별로 영구 저장합니다.
   저장된 클러스터를 다시 선택하면 API 호출 없이 저장 결과가 복원되며,
   버튼이 **다시 분석**으로 바뀝니다(재분석 시 덮어쓰기).
4. **초기화**: "모든 데이터가 삭제됩니다" 확인 다이얼로그에서 **확인**을 누르면
   해당 클러스터의 저장 결과가 삭제되고 분석 대기 상태(버튼 라벨
   '정합성 분석 실행')로 되돌아갑니다.

## 탭 2 — 제·개정규정 정합성

제·개정 예정 규정 PDF를 업로드하여 상위법령·현행 대학규정과의 정합성을 분석합니다.

1. **PDF 업로드**: 여러 파일을 한 번에 선택할 수 있습니다.
2. **정합성 분석 실행**: 업로드한 각 PDF에서 regulation_parser 와 동일한 방법
   (표 보존 추출 → 좌표 기반 재구성 폴백 → 장/조 구조화 파싱)으로 텍스트를 추출해
   `regulationsByCluster/M. 제개정규정통합.txt`를 생성합니다(150KB 초과 시 `M1`, `M2`…로 분할).
   본문 시작점을 찾지 못한 PDF는 원문 전체를 규정명 블록으로 포함합니다.
   이후 통합 파일 개수만큼 `분석모드:제개정규정` 프롬프트로 API를 반복 호출하고 결과를 합산합니다.
3. **결과 저장·표시**: 업로드 파일명 조합을 키로 `analysis_store.json`에 저장하며,
   앱 재접속 시 마지막 분석 결과가 복원됩니다. 같은 파일 조합을 재분석하면 덮어씁니다.
4. **초기화**: 확인 다이얼로그에서 **확인** 시 마지막 표시 결과를 해제합니다
   (과거 분석 이력 entries 는 보존).

## 분석 결과 화면

- **요약 카드**: "상위법령 ↔ 대학규정", "대학규정 ↔ 대학규정"(제개정 탭은 ↔ 제개정규정)
  별 정합성 불일치/검토필요 건수를 표시합니다.
- **이슈 목록**: 비교유형(lr/ir) × 상태(불일치/검토 필요) 4개 그룹으로 나누어
  심각도(1~5) 순으로 정렬해 표시합니다. 항목을 클릭하면 관련 내부 규정·상위법령·
  근거·수정 권고안 상세가 펼쳐집니다.
- **검증완료 토글**: 항목별로 검토 완료 처리(회색 표시, 목록 하단 이동)할 수 있습니다.
- **필터/전체 펼치기·접기**: 불일치/검토 필요 분류 필터를 제공합니다.
- **부분 분석 경고**: Agent 가 `status: partial`로 응답하면 경고 박스에 사유를 표시합니다.
- **API 입력 정보·최근 분석일**: 전송한 파일명/크기와 분석 시각을 함께 표시합니다.

## Agent 응답 처리

- Agent 는 정해진 JSON 스키마(schema 1.1: `analysis`, `retrieval_report`, `issues[]`)로
  응답하며, 마크다운 코드펜스나 설명문이 섞여 있어도 첫 번째 완전한 JSON 객체만
  관대하게 추출합니다.
- 분할 호출 결과 합산 시 `issue_id` 일련번호를 접두어별로 001부터 재부여해
  중복을 방지하고, `partial` 상태와 경고 목록을 병합합니다.
- 마지막 Agent 응답 원문은 디버깅용으로 `last_agent_response.txt`에 저장되므로
  JSON 파싱 실패 시 전체 응답을 확인할 수 있습니다.

## 결과 저장 파일 (`analysis_store.json`)

```json
{
  "current":  { "A": { "agent_json": …, "dashboard_data": …, "request_info": …, "analyzed_at": "…" }, … },
  "revision": { "entries": { "파일명1|파일명2": { … } }, "last_key": "…" }
}
```

임시파일 작성 후 원자적 교체(`os.replace`)로 저장하여 기록 중 손상을 방지합니다.

```powershell
# 가상환경 생성(선택) 후 의존성 설치

## 폴더 구성

```
Regulations_Parser/
├── regulation_parser.py        # 규정집 파서 (메인)
├── streamlit_dashboard.py      # 정합성 평가 대시보드 (Streamlit)
├── requirements.txt            # 의존성 목록
├── .streamlit/secrets.toml     # FACTCHAT_API_KEY (커밋 금지)
├── .env                        # FACTCHAT_API_KEY 폴백 (커밋 금지)
├── regulations.db              # 규정 DB (파서 실행 시 생성/갱신)
├── regulations_delete.db       # 사라진 규정 보관 DB
├── analysis_store.json         # 대시보드 분석 결과 영구 저장

## 참고 사항

- 파서 실행에는 그룹웨어 규정집 페이지에 접근 가능한 네트워크 환경이,
  대시보드 실행에는 FactChat API 접근 권한(API 키)이 필요합니다.
- PDF가 아닌 형식(HWP 등)의 규정 파일은 텍스트 추출을 생략하고 메타데이터만 저장합니다.
- 통합 텍스트 파일은 실행 날짜가 파일명에 포함되므로 실행할 때마다 새 파일이 생기며,
  이전 날짜 파일은 자동 삭제되지 않습니다.
